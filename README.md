# LogiBridge / LogiEdge — Edge AI Predictive Maintenance Pipeline

An end-to-end Edge AI + IoT pipeline that simulates truck sensor data (temperature,
vibration), classifies truck health in real time using a TensorFlow Lite model, and
monitors the live prediction stream for data/model drift using Population Stability
Index (PSI).

No physical hardware is required — sensors are simulated in software and everything
runs locally over MQTT.

---

## 1. Architecture

```
Sensor Simulator (temperature, vibration)
            │  MQTT
            ▼
      Mosquitto Broker (localhost:1883)
            │
            ▼
   Inference Service (sliding window → normalise → TFLite model)
            │  MQTT (publishes classification result)
            ▼
   ┌────────┴─────────┐
   │                   │
Console output    Drift Monitor (PSI vs reference distribution)
(OK / ALERT)      (flags [LOGIBRIDGE DRIFT ALERT] on distribution shift)
```

**Classes predicted:** `Normal` (0), `Warning` (1), `Critical` (2)

Deployment side: the inference service is packaged into a Docker container so that
only the model file needs to change on an over-the-air (OTA) update, not the whole
application. An Ansible playbook pushes that update to fleet trucks in a repeatable,
idempotent way.

## 4. Setup (one-time)

### 4.1 Clone the repo and create a virtual environment

```powershell
git clone <your-repo-url> logibridge
cd logibridge
python -m venv venv
```

### 4.2 Activate the virtual environment

**Windows (PowerShell):**
```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned
.\venv\Scripts\Activate.ps1
```

**Windows (Git Bash):** `Activate.ps1` will not run in Git Bash — use the Unix-style
activation script instead, from inside the venv folder:
```bash
source venv/Scripts/activate
```

**macOS / Linux:**
```bash
source venv/bin/activate
```

### 4.3 Install dependencies

```powershell
pip install -r requirements.txt
```

### 4.4 Install and start Mosquitto

- Download from https://mosquitto.org/download/ and install.
- Confirm it's running and listening on port 1883:

```powershell
Get-Service -Name mosquitto     # Windows, if installed as a service
```

If it isn't running as a service, start it manually in its own terminal:
```powershell
mosquitto -v
```

### 4.5 Set the broker host environment variable

The code defaults `BROKER_HOST` to `mosquitto`, which is the hostname used when
running inside Docker on the same network as the broker container. When running
natively on your laptop (not in Docker), `mosquitto` will not resolve — you must
point it at `localhost` instead.

**Set it once, permanently, for your user account (recommended):**
```powershell
[System.Environment]::SetEnvironmentVariable("BROKER_HOST", "localhost", "User")
```
Close and reopen your terminal(s) after running this for it to take effect.

**Or set it per-session, in every new terminal you open:**
```powershell
$env:BROKER_HOST = "localhost"
```

### 4.6 Make sure the model file is in place

`inference_service.py` loads `inference/model.tflite` by default. If it's missing,
copy one of the trained models there:

```powershell
copy training\models\m3_pruned_int8.tflite inference\model.tflite
```
(`m3_pruned_int8.tflite` is recommended — smallest size, fastest inference.)

## 5. Running the ML pipeline

You need **three terminals running at the same time**, each with the venv
activated. Open a new terminal for each of the steps below and run them in order.

### Terminal 1 — Inference service

```powershell
cd logibridge
.\venv\Scripts\Activate.ps1
$env:BROKER_HOST = "localhost"
python inference\inference_service.py
```

Wait for exactly this line, then leave it running:
```
[inference] connected to localhost:1883, model=...\inference\model.tflite, backend=tensorflow.lite
```

### Terminal 2 — Sensor simulator

```powershell
cd logibridge
.\venv\Scripts\Activate.ps1
$env:BROKER_HOST = "localhost"
python data_pipeline\simulator.py --anomaly none
```

Options for `--anomaly`: `none`, `temp_drift`, `vibration`, `combined`.

Each run lasts 300 seconds by default. For a longer, uninterrupted run — useful
when recording a demo, since it avoids the brief gap in the sensor stream that a
restart causes — set `--duration` explicitly instead:
```powershell
python data_pipeline\simulator.py --anomaly none --duration 7200
```
(`7200` seconds = 2 hours. Note `--duration` runs a single anomaly mode for its
whole duration; stop it with `Ctrl+C` and rerun with a different `--anomaly` value
to switch modes.)

If you'd rather have it restart automatically instead of using `--duration`, this
loop works too, restarting every 300 seconds:
```powershell
while ($true) {
    python data_pipeline\simulator.py --anomaly none
    Start-Sleep -Seconds 1
}
```
Press `Ctrl+C` to stop the loop when you're done.

Within ~10-15 seconds, Terminal 1 should start printing:
```
[OK] {'truck_id': 'TRK-001', ..., 'class_label': 'Normal', 'confidence': 0.99...}
```

### Terminal 3 — Drift monitor

**First time only** — build the reference distribution (needs Terminal 1 + 2
running and producing `Normal`-class results; takes several minutes):
```powershell
cd logibridge
.\venv\Scripts\Activate.ps1
$env:BROKER_HOST = "localhost"
python monitoring\drift_monitor.py --mode build-reference --truck-id TRK-001
```
Wait for:
```
[drift_monitor] saved reference distribution -> ...\monitoring\reference_dist.json
```
This only needs to be done once — `reference_dist.json` is reused on subsequent
runs. If you rebuild it, remember to `git add` / `git commit` / `git push` the
updated file so the repo stays in sync with what the video demonstrates.

**Then start live monitoring:**
```powershell
python monitoring\drift_monitor.py --mode monitor --truck-id TRK-001
```

The monitor waits for a full rolling window of 100 inferences before printing
anything (roughly 15-17 minutes at the simulator's ~10s emission interval), then
prints a PSI score every 60 seconds:
```
[drift_monitor] n=100 PSI=0.137
```

If `PSI > 0.25`, it also prints:
```
[LOGIBRIDGE DRIFT ALERT] PSI=0.xxx
```

**To see a real drift alert fire**, once baseline monitoring is stable, switch
Terminal 2 to `--anomaly combined` and watch PSI climb over the following minutes.
Switch back to `--anomaly none` afterwards to see PSI recover.

## 6. Docker — building the inference container

Needed for the OTA/deployment demo. Requires Docker Desktop installed and running
(check the whale icon in the system tray is steady, not animating, before running
any `docker` command).

```powershell
cd logibridge
docker build -f inference\Dockerfile -t logibridge-inference:latest .
```

**To simulate an OTA model update:**
```powershell
copy training\models\m2_ptq_int8.tflite inference\model.tflite -Force
docker build -f inference\Dockerfile -t logibridge-inference:latest .
```
Compare the two build outputs — since only the model file changed, every layer up
to `COPY inference/model.tflite .` should show `CACHED` on the second build, and
only that layer and the ones after it actually rebuild. This is the property that
keeps OTA updates small: only the changed layer needs to be pushed to each truck,
not the full image.

If `docker` isn't recognised in your terminal even after installing Docker
Desktop, the CLI's install folder likely isn't on your PATH yet — add
`C:\Program Files\Docker\Docker\resources\bin` under **Environment Variables →
Path**, then open a brand-new terminal (existing ones won't pick up the change).

## 7. Ansible — OTA deployment demo

Ansible does not run as a control node on native Windows — it needs a
POSIX-compliant shell, so this section runs inside **WSL2**.

### 7.1 One-time WSL + Ansible setup

Check for an existing WSL distro:
```powershell
wsl --list --verbose
```
If nothing is listed, install one (requires a reboot the first time):
```powershell
wsl --install -d Ubuntu
```

Inside Ubuntu (`wsl -d Ubuntu`):
```bash
sudo apt update
sudo apt install -y ansible python3-pip
pip3 install docker --break-system-packages
```

Then, in **Docker Desktop → Settings → Resources → WSL Integration**, enable the
toggle for your Ubuntu distro and click **Apply & Restart**. This lets Ansible
and Docker inside WSL see the same images and containers as Docker Desktop on
Windows — without this step, `docker build` in PowerShell and `docker` commands
inside WSL are two separate, disconnected engines.

If `docker` commands inside WSL return a permission error on the daemon socket,
add your user to the `docker` group once, then close and reopen the WSL session
completely for it to take effect:
```bash
sudo usermod -aG docker $USER
```

### 7.2 Local inventory setup

The default `deployment/inventory.ini` targets real fleet hardware over SSH
(`ansible_host=192.168.1.101`, etc.), which won't be reachable when demonstrating
locally. For a local run, point it at `localhost` instead:

```ini
[truck_edge_nodes]
localhost ansible_connection=local
```

### 7.3 Push the image to a local registry and run the playbook

From inside WSL, in the project directory (`/mnt/d/...` on Windows drives):
```bash
cd /mnt/d/Mini-Project-ML/logibridge
docker run -d -p 5000:5000 --name registry registry:2
docker build -f inference/Dockerfile -t logibridge-inference:latest .
docker tag logibridge-inference:latest localhost:5000/logibridge-inference:latest
docker push localhost:5000/logibridge-inference:latest
```

The playbook's tasks run with elevated privileges (`become: true`), so pass `-K`
to be prompted for the sudo password once at the start:
```bash
ansible-playbook -i deployment/inventory.ini deployment/logibridge_deploy.yml -K
```

Run it a second time to check for idempotency:
```bash
ansible-playbook -i deployment/inventory.ini deployment/logibridge_deploy.yml -K
```

**Known limitation (see section 8):** tasks 1, 2, 3, and 5 report `ok` (no
change) on the second run, as expected. Tasks 4 and 6 currently report `changed`
on every run — this is a documented `community.docker` collection behaviour, not
an application bug (details below).

## 8. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `ValueError: Could not open '/app/model.tflite'` | `MODEL_PATH` env var is set, or the script wasn't saved before running | Check `echo $env:MODEL_PATH`; unset with `Remove-Item Env:MODEL_PATH` if set. Otherwise re-save the file. |
| `socket.gaierror: [Errno 11001] getaddrinfo failed` | `BROKER_HOST` is still the Docker default (`mosquitto`), which doesn't resolve outside Docker | `$env:BROKER_HOST = "localhost"` before running, or set it permanently (see 4.5) |
| `[inference] connected...` line repeats in a loop | Two processes with the same MQTT client ID are fighting over the connection (usually a leftover process from an earlier run) | `Get-Process python` to check for duplicates, then `Stop-Process -Name python -Force` and restart cleanly |
| `python: can't open file 'simulator.py'` | Wrong path — the script lives in `data_pipeline\`, not a `simulator\` folder | `python data_pipeline\simulator.py --anomaly none` |
| Drift monitor stuck at `collected 0/300` | No live data is being published while `build-reference` is running | Make sure Terminal 1 (inference) and Terminal 2 (simulator, `--anomaly none`) are both running at the same time |
| `docker` not recognised in PowerShell | Docker Desktop's CLI folder isn't on PATH, or you're using a terminal window opened before the PATH change | Add `C:\Program Files\Docker\Docker\resources\bin` to PATH, then open a brand-new terminal |
| `failed to connect to the docker API at npipe:...` | Docker Desktop CLI is installed but the engine app isn't running | Open the Docker Desktop app and wait for the whale icon in the system tray to stop animating |
| `permission denied ... docker.sock` inside WSL | Your WSL user isn't in the `docker` group yet | `sudo usermod -aG docker $USER`, then fully close and reopen the WSL session |
| `sudo: a password is required` during `ansible-playbook` | The playbook uses `become: true` but wasn't told to prompt for the password | Add `-K` to the command: `ansible-playbook ... -K` |
| Ansible playbook fails reaching `192.168.1.10x` hosts | `inventory.ini` still points at real fleet IPs over SSH | Switch to `localhost ansible_connection=local` for local testing (see 7.2) |
| Ansible run shows `changed` on tasks 4 & 6 every time, even on repeat runs | Known `community.docker` collection limitation: the module compares the container's stored image digest against the desired image *tag*, which never match exactly even when the image is genuinely unchanged (see the `image_name_mismatch` deprecation warning in the task output) | Document as a known limitation rather than a bug — tasks 1, 2, 3, and 5 are genuinely idempotent, which demonstrates the deployment logic works correctly |

## 9. Known limitations / design notes (useful for report & viva)

- **PSI needs a full rolling window (100 samples) to be statistically meaningful.**
  The monitor intentionally withholds output until the window fills, rather than
  computing PSI on partial data.
- **The reference distribution is built only from `Normal`-class confidence scores**
  (`class_id == 0`), while the live rolling window includes confidence scores from
  *all* predicted classes. Occasional false-positive `Warning`/`Critical`
  classifications on clean sensor data will therefore nudge live PSI upward even
  without genuine drift — this shows up as a moderate baseline PSI (~0.10-0.25)
  under steady-state `--anomaly none` operation, which is expected behaviour, not a
  bug.
- **Drift detection has a natural lag** corresponding to the rolling window size:
  since the window only replaces one sample at a time (deque with `maxlen=100`),
  PSI rises gradually over several checks after an anomaly begins, rather than
  jumping instantly.
- **Ansible idempotency is partial by design of the tooling, not the playbook.**
  Directory creation, model file copy, reference file copy, and image pull are
  fully idempotent. Container stop/recreate re-triggers every run because of how
  the `community.docker` collection currently compares a running container's
  image digest against a tag reference — a module-level limitation, documented in
  its own deprecation warnings, rather than a flaw in the deployment logic itself.
- **Simulated hardware only.** No physical Raspberry Pi / Jetson / STM32 device is
  used; the written comparison of edge hardware options is an analysis exercise
  based on published specifications, not a deployment.

## 10. Model variants (for benchmarking discussion)

| Model | File | Notes |
|---|---|---|
| FP32 baseline | `training/models/m1_fp32.tflite` | Largest, most accurate |
| Post-training quantised INT8 | `training/models/m2_ptq_int8.tflite` | Smaller, faster |
| Pruned + quantised INT8 | `training/models/m3_pruned_int8.tflite` | Smallest, fastest — used by default in `inference/model.tflite` |

Run `optimisation\benchmark.py` to reproduce size/latency comparisons across the
three variants. Note that on a desktop x86 CPU, the FP32 model can benchmark
faster than the quantised variants — this is expected, since x86 lacks the INT8
SIMD optimisations (e.g. ARM NEON on Raspberry Pi) that make quantisation pay off
in practice; the actual target hardware would be expected to reverse this result.
